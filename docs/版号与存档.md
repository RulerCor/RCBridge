# RCBridge 版号与存档

## 版号怎么定

`bridge/VERSION` 是当前构建的唯一版号来源，格式是 `主版.功能版.修订版`：

| 改动 | 版号 | 示例 |
| --- | --- | --- |
| 兼容性修复、打包调整 | 升修订版 | `0.1.1 → 0.1.2` |
| 向后兼容的功能新增 | 升功能版，修订版归零 | `0.1.1 → 0.2.0` |
| 用户需要迁移配置，或已有接入无法继续使用的破坏性变更 | 升主版，后两位归零 | `0.1.1 → 1.0.0` |

Git 标签加 `v`，例如 `v0.1.1`。变更记录中的旧版号不用改。已经归档的 ZIP 不替换，已打的标签不移动；发现问题就升新版本。

## 各目录放什么

| 位置 | 用途 |
| --- | --- |
| Git 提交与 `vX.Y.Z` 标签 | 追溯每个已归档版本的源码 |
| `archives/releases/vX.Y.Z/` | 对外可交付的 ZIP、`SHA256SUMS.txt`、`BUILD.txt`（源码提交号等） |
| `archives/pre-split/` | 拆分前的成品和开发资料，只作历史参考，不是独立版发布来源 |
| `dist/` | 保留原有独立版交付目录；以后不作为正式归档位置 |
| `build/`、`toolchain/` | 临时构建和本机工具链，不提交到 Git |

`v0.1.0` 下保留旧 ZIP 原名 `RCBridge-win-x64.zip` 和原校验值。比对过原包 `app/` 下的文件与当时工作区的对应文件，内容一致（文本换行差异不计）；Git 标签是补录的源码基线，不能证明旧 EXE 来自该提交。`v0.1.1` 起由脚本记录实际打包的提交。

归档不包含本机 `%LOCALAPPDATA%\RCBridge`、账号配置、日志或消息数据；不打包微信等第三方应用的安装程序。`archives/` 不进 Git。若要防止磁盘损坏或误删，把成品归档和 Git 仓库分别备份到其他磁盘或设备；没有远程仓库时可用 `git bundle create RCBridge-history.bundle --all` 另存 Git 历史和标签。

## 归档新版本

1. 更新 `bridge/VERSION` 和 `CHANGELOG.md`，提交该版本的所有源码，确保工作区干净。构建环境见 [使用与构建指南](使用指南.md#维护与验证)。
2. 在仓库根目录运行：

   ```powershell
   ./toolchain/python/python.exe -X utf8 archive_release.py
   ```

   脚本会运行单元测试、构建 Windows x64 便携包，并用模拟 WeRC 与 OneBot 做离线收发验证。成功后才写入新版本归档目录；同版已归档或已有 Git 标签时会拒绝重复操作。
3. 执行脚本末尾打印的 `git tag -a ...` 命令。标签指向 `BUILD.txt` 中的 `commit`。整个流程只在本地执行，不发布或推送。

## 核验与回退

在归档目录执行下面的 PowerShell 命令。每个版本目录应只有一个 ZIP：

```powershell
$zip = Get-ChildItem -File -Filter *.zip
$sha = ((Get-Content -LiteralPath SHA256SUMS.txt -Raw).Trim() -split '\s+', 2)[0]
if ((Get-FileHash -LiteralPath $zip.FullName -Algorithm SHA256).Hash -ne $sha) {
    throw 'ZIP 的 SHA-256 不匹配'
}
```

回退程序时，关掉当前版本，备份 `%LOCALAPPDATA%\RCBridge`，将旧 ZIP 解压到另一个目录再启动旧 `RCBridge.exe`。不要拿旧包覆盖新包目录；如果该版本有配置迁移，使用升级前的用户配置备份。只想查看旧源码时用 `git show vX.Y.Z` 或检出对应标签到独立目录，不必移动当前分支。
